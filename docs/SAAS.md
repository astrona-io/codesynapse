# CodeSynapse as a multi-tenant product

This is the target architecture for running CodeSynapse as an open-source, self-hostable SaaS product on Kubernetes. It is built in phases; each completed phase is committed, pushed and opened as its own pull request. Decisions below were agreed on 2026-10-22.

## Who it is for

Engineering teams and the people around them (team leads, security and compliance, platform owners) who are not AI or data specialists. They know that model tokens cost money, that security issues and vulnerable dependencies matter, and that the wrong licence can be expensive. The product answers in that language: what needs attention, what it costs, and what to do next.

## Concepts

| Concept | Meaning |
|---|---|
| **User** | A person with an email address. Logs in with a password (argon2id) or single sign-on (OpenID Connect). |
| **Organisation** | The tenant. Owns repositories, reviews, agent memory, statistics and settings. A user can belong to several. |
| **Membership** | A user's role in an organisation: `owner`, `admin`, `member`, `viewer`. |
| **API key** | A personal key (`csk_…`) bound to one user and one organisation. Agents (MCP), hooks and the CLI use it. Shown once, stored only as a SHA-256 hash, revocable, with last-used time. |
| **Root** | The account that set up the installation. Governance only: settings, health, telemetry, audit and account recovery. It cannot do organisation work, whatever memberships, grants, keys or jobs it has; setup hands over to a standard owner. See [root bootstrap](ROOT_BOOTSTRAP_PLAN.md). |
| **Platform admin** | Operates the installation: sees cross-tenant operational statistics and manages users. Root is one; standard accounts can be granted the flag. Explicit organisation membership and repository permission are required for code access. |
| **Repository** | An organisation's view of a code base (remote, branch, schedule, settings). |
| **Graph** | The indexed code graph of a repository at a commit, in HugeGraph. Shared between organisations when allowed (below). |

## Data

- **PostgreSQL** holds relational, tenant-owned data: users, organisations, memberships, sessions, API keys, invitations, settings, audit log, and (from phase 2) the repository registry and reviews.
- **HugeGraph** keeps code graphs, agent memory and usage counters, scoped by organisation from phase 2; **Milvus** keeps memory vectors. (Neo4j did this until it was removed in October 2026.)
- **No source bodies** are stored anywhere, as before (AGENTS.md).

### De-duplication

The same repository is indexed once, not once per organisation:

- A graph is keyed by its remote and commit. Organisations reference graphs through their repository entries.
- **Public repositories** are shared by every organisation that adds them.
- **Private repositories** are shared only between organisations that each proved access with their own token (a successful fetch of the same remote and commit). Otherwise each organisation gets its own graph.
- Organisation-owned data (reviews, memory, decisions, schedules, settings) is never shared.

## Authentication and authorisation

- **Sessions:** login sets an HTTP-only, `SameSite=Lax`, `Secure` (behind TLS) cookie holding a random token; only its hash is stored. Sessions expire after 14 days and on logout or password change.
- **API keys:** `Authorization: Bearer csk_…`. Every MCP connection, hook and CLI call uses one, so usage, memory and reviews are attributed to a user and organisation and never mix.
- **Service token:** manages platform operations only in accounts mode; content calls require an authenticated organisation-scoped principal. Explicit single-tenant/offline mode remains supported.
- **Without a database** (`CODESYNAPSE_DATABASE_URL` unset) the API runs single-tenant exactly as before.
- **Brute force:** failed logins are rate limited per email and per client address.
- **Audit log (NIS2):** every changing request (route, target, status, outcome) and every security event (sign-up, login success and failure, rate limiting, logout, password change, key creation and revocation, organisation and membership changes, refused requests) with actor, authentication method, key, organisation, client address, user agent and request ID. Entries are append-only and hash-chained (each hash covers the entry and the previous hash; `GET /api/v1/admin/audit/verify` checks the chain), exportable as JSON, JSON Lines or CSV (organisation admins: their organisation; platform admins: everything), written as structured `audit` log lines for SIEM collection, and kept `CODESYNAPSE_AUDIT_RETENTION_DAYS` (default 400).
- **Permissions:** organisation administration is separate from repository access. Organisation defaults are `READ_ONLY` or `NONE`; direct user overrides take precedence over team grants, then organisation defaults. Repository `READ` permits navigation, `WRITE` adds reviews/memory writes, and `ADMIN` adds sync, schedules and access management. New and migrated organisations default to `NONE`. See [the access-control implementation](ACCESS_CONTROL_PLAN.md#implementation-and-upgrade) for migration and conflict rules.

## Product structure (web app, phase 3)

A calm product UI with light and dark themes, neutral surfaces, one brand accent and status colours only for meaning. Plain language, an explanation next to every figure, and costs in money where possible.

1. **Overview**: what needs attention now across the organisation (critical security findings, vulnerabilities you actually call, licence conflicts, stale repositories), and what agents saved.
2. **Repositories**: list with health at a glance; each repository has Summary, Security, Licences, Dependencies, Code health, Reviews and Memory.
3. **Agents**: connect an agent in three steps (create a key, copy the setup for Claude Code / Codex / Cursor, verify), then see sessions, tokens saved and memory.
4. **Settings**: organisation (members and roles, Git tokens per host, AI models, licence policy, sync defaults) and personal (profile, password, API keys, sessions).
5. **Administration** (platform admins): system health, organisations, users (suspend, platform admin), cross-tenant statistics and the audit log.
6. **Help**: getting started and "what does this mean" pages linked from every screen.

## Phases

1. **Accounts and audit** (done): PostgreSQL with embedded migrations; users, organisations, memberships, sessions, API keys; the hash-chained audit log with export and verification; signup (first user is platform admin), login, logout, `me`, organisations and members, personal API keys; auth middleware accepting session, API key or the legacy service token; single-tenant mode unchanged without a database.
2. **Tenant scoping**, in three parts:
   - **2a (done):** repository registry in PostgreSQL (`repositories`: organisation, graph, remote, visibility); every API route carries an authorisation policy; lists, overview, statistics and jobs show the organisation's repositories only; other organisations' repositories, reviews and jobs answer 404; an organisation adding an already indexed public repository is linked to the existing graph (de-duplication); organisations add public repositories only, cloned without the installation's tokens; deleting removes the link and the graph with the last link; organisation owners can link verified remote graphs (`POST /api/v1/accounts/orgs/{org}/repos`); phase 4d closes the old platform attachment bypass.
   - **2b (done):** the MCP server authenticates personal API keys (checked on every request, so revocation and removed memberships take effect at once) and scopes every tool to the key's organisation; agent memory is kept per organisation even on a shared graph (`org|graph` namespaces, also for the API's offload and recall); reviews carry their organisation; usage counters carry the organisation and the statistics show an organisation its own; calls the MCP server makes to the API on a user's behalf use that user's key.
   - **2c (done):** organisation Git tokens per host (`PUT/DELETE /api/v1/accounts/orgs/{org}/git-tokens/{host}`, owners and admins), sealed with AES-256-GCM under `CODESYNAPSE_SECRET_KEY` and bound to organisation and host; members see host and preview. Organisations add private repositories after proving access with their own token (one `ls-remote`); the clone, syncs, branch lists and fix-branch pushes use it, never the installation's tokens. A graph is shared only between organisations that each proved access, and only for the same remote. Every sync re-checks each organisation's access: a refused or removed token hides the graph from that organisation (audited) until a working token restores it; network failures change nothing. Also fixed on the way: organisations could not add public repositories without naming a branch, and a public URL registered under a private graph's name would have linked that graph.
2d. **Relationship-based access (ReBAC)** (done): Zanzibar-style relation tuples in PostgreSQL with a Go engine (no extra service). Teams in organisations (members and maintainers, with an organisation role for the whole team); a guest role that inherits nothing; per-repository grants to people and teams (viewer, editor, admin); legacy cross-organisation sharing (inactive after phase 4d until explicit membership and a grant exist); reviews and agent memory follow the repository's grant. The API and MCP compute access the same way; agents of viewers and share recipients are read-only; every grant change is audited. UI: Settings → Teams, and an Access page on each repository.
3. **New web app**, in two parts:
   - **3a (done):** the calm design system (light and dark, one accent, status colours for meaning, validated chart palettes per theme) applied to every page through tokens; sign-in, sign-up and first-run setup; the web proxy forwards the user's session instead of the installation token (which made every visitor a platform admin) and reports the client address to the API through `CODESYNAPSE_TRUSTED_PROXIES`; organisation switcher; Settings (profile and password, API keys, members and roles, Git tokens); Agents (create a key, copy the setup for Claude Code, Codex, Cursor or any MCP client, see the first call arrive); Help (getting started and what every figure means).
   - **3b (done):** Overview is "what needs attention" (`GET /api/v1/attention`, also per repository with `?repo=`): called vulnerabilities, critical and high findings, licence conflicts, private repositories that lost access, failing syncs, other vulnerabilities, repositories no security rule covers, stale indexes and missing update automation, ranked and each with a plain explanation and a link to where it is fixed; repositories with nothing flagged are listed as all clear. Repository pages are grouped as Repository (Summary with its own attention list, Security, Dependencies, Licences, Code health = Quality + Unused code, Access), Work (Reviews, Agent memory, Impact of a change, AI assistant) and Explore (Graph, Symbols, Kubernetes & Helm, Docs, Packages). The new Dependencies page lists every package with version, licence verdict, vulnerabilities with reachability and fixed version, and the Renovate and Dependabot findings.
4. **Administration, access isolation and retrieval**:
   - **4 (done):** the Administration area for platform admins. Overview: health of the graph store, accounts database, live statistics and audit chain, with timings; counts of people, organisations and repositories; unassigned repository counts (phase 4d hides their names and removes platform assignment); tool calls by organisation, model cost and latency over 24 hours, 7 or 30 days. Organisations: members per role, repositories, repositories that lost access, teams. Users: memberships, active API keys, last agent use; suspend and resume accounts (a suspended account is signed out everywhere, cannot sign in and its keys stop working, while memberships and history stay) and grant or revoke platform admin, never leaving the installation without an active admin and never suspending yourself. Audit log: filters by kind of action, person, outcome and period, entry details, CSV and JSON Lines export of the filtered period, and chain verification. Every change is audited (`user.suspend`, `user.resume`, `user.platform_admin.grant|revoke`).
   - **4b, privacy and model cost (done):** personal data is masked in free text before it is stored or sent to a model (`redact.Personal`, and `redact.Free` for secrets plus personal data): payment card numbers (issuer prefix, length and Luhn), national identity numbers (US SSN with unissued ranges excluded; Nordic DDMMYY/YYMMDD/YYYYMMDD-NNNN with a real date, eight-digit dates not in the future) and phone numbers (international with +, North American, and eight digits in pairs), replaced by `[CARD]`, `[NATIONAL-ID]` and `[PHONE]` so the sentence still reads. It applies to agent memory names, offloaded turns, review text, every model prompt and every embedding input. Only formatted or validated numbers match; hashes, versions (including semver build metadata), line numbers, timestamps, UUIDs, IP addresses, dates and diff hunks are left alone (tested, and fuzzed for idempotence). Ingest summaries keep secret redaction only. Anthropic calls mark the system prompt (always a constant) as the cache prefix, so repeated calls of a task read it from the prompt cache once it is longer than the model's minimum; cached tokens count in `llm_tokens_saved_total` and in the cost. Nearest-neighbour memory search returns 3 to 10 hits (8 by default; was up to 50) in every store (`vector.ClampK`).
   - **4c, search (done):** `docs/adr/0001-search.md` compares search inside the stores we run (Milvus BM25 and dense vectors with RRF, HugeGraph and Neo4j indexes) with a separate engine fed by change data capture (Elasticsearch, which is not Apache-2.0 compatible, or OpenSearch/Solr, which are) on footprint, freshness, tenant isolation and revocation, latency, answer size and licences, and keeps search in the stores. Agent memory recall is now hybrid in the proper sense: a BM25 leg over the namespace's entity names, aliases and types (`MemoryLexical`, one ranker for all three stores, about 5 ms at the 5,000-entity cap) and the vector leg are fused by reciprocal rank, deduplicated and cut to 3–8 entries, each saying which legs found it; both legs read only the caller's namespace, and answers never carry vectors. Before, vector and substring scores were mixed as if on one scale. Code search keeps exact identifier lookup first and graph traversal for structure (source is not embedded). The ADR names when to move a leg into Milvus' native BM25 (longer text such as doc sections and reviews, p95 above 50 ms, larger memory caps) and the only conditions under which a separate engine would be worth it.
   - **4d, platform isolation and repository permissions (implemented):** removed the API/MCP platform-admin and service-token content bypasses. Requires explicit organisation membership, supports user/team grants and organisation read/none defaults, and distinguishes repository read, write and admin actions. Includes a versioned access projection for Neo4j/HugeGraph without making stale graph data an authorization source. [Implementation plan](ACCESS_CONTROL_PLAN.md): schema mapping, Cypher/Gremlin candidates, authoritative Go resolver, HTTP/stdio enforcement, migration of existing shares and parity/security tests.
   - **4d follow-up, bootstrap root separation (implemented):** the first account is an immutable bootstrap root (one per installation) limited to governance. Setup creates the first organisation and a standard owner in one transaction and ends the root session. Every API route and MCP tool is classified; root is refused business work through memberships, grants, keys, execution sessions, queued jobs and schedules. Existing installations are classified at start-up from their setup history; ambiguity limits platform administrators until `codesynapse-api designate-root`. [Plan and implementation](ROOT_BOOTSTRAP_PLAN.md).
   - **4e, tenant telemetry and four dashboards (implemented):** OTel metrics exported to VictoriaMetrics with authenticated tenant, accepted MCP tool and configured provider/model attribution. Dashboard groups: token/model cost, network/cloud bandwidth, database latency and memory/offloading. [Implementation plan](TELEMETRY_PLAN.md): metric types and current-name compatibility, measured versus estimated savings, bounded cardinality, fixed tenant-filtered MetricsQL, dependency review and integration checks. This replaces the earlier OTel deferral with the approved v1.47.0 SDK/exporter. Full race tests, lint, vet, web build and native VictoriaMetrics/dashboard integration checks passed. Cloud savings remain unmeasured without an equivalent fallback; missing usage/prices remain unknown.
   - **4f, graph/vector context reduction (implemented):** bounded structured responses, exact identifier priority, current-graph recall validation and tenant-safe hydration across all stores. [Implementation and conditional Milvus migration](RETRIEVAL_PLAN.md); [reproducible measurements](RETRIEVAL_RESULTS.md). Shared BM25/RRF remains in Go: lexical p95 at 5,000 entities is 4.74 ms, below ADR 0001’s 50 ms migration trigger. The small fixture has negative aggregate token savings after full MCP framing; no production SLA improvement is claimed.
   - **4g, immutable session context (done):** one runtime-supplied primary ID per thread, registered to one tenant and participant, inherited by MCP, subprocesses, models and queued work. Missing/conflicting context fails closed. Separate session graph/vector memory, fixed expiry, replay tombstones and explicit promotion preserve durable repository memory. [Contract and migration](SESSION_CONTEXT_PLAN.md) covers API/HTTP/stdio integration, limits and adversarial tests. Accounts and a runtime-aware client are required; the dashboard binds each signed-in browser session itself. Session IDs remain out of metric labels.
   - **4h, repository configuration and annotation (implemented):** strict repository-root `.codesynapse.yaml` parsing, shared ingestion filters, explicit exclusion approval, tenant-local finding suppressions, and bounded local annotation of indexed symbol metadata. Graph replacement is atomic; approvals and annotations live in PostgreSQL. The Indexing policy page shows the indexed configuration, coverage, approvals and current annotations. [Configuration reference](REPO_CONFIG_PLAN.md) covers approval, runtime identity, queue limits and migration. Benchmarks record the policy digest.
   - **4i, ingestion transparency (implemented):** report files encountered, indexed and skipped with explicit reasons, annotation-job outcomes and estimated token savings. [Implementation plan](INGEST_TRANSPARENCY_PLAN.md): exact per-run accounting, scanner versus whole-file exclusions, bounded opaque repository labels, tenant-owned `Repository.metrics` reports and dashboard/audit coverage. Depends on 4h policy decisions and 4e telemetry; session context follows 4g.
   - **4j, code architecture audit and upgrade assessment (completed):** [Audit results](CODE_ARCHITECTURE_AUDIT.md) inventory the current stack, reproduce parsing/edit-validation gaps, compare upstream packages and record profiles and reproducible benchmarks. The [assessment plan](CODE_ARCHITECTURE_AUDIT_PLAN.md) is fulfilled by tests and documentation; production upgrades are proposed as separate 4j.1–4j.7 PRs. Priorities are edit validation, final prompt preflight and measured allocation reductions. New dependencies, native parsers and interactive-editor work remain conditional. The agent guide documents MCP capability/freshness checks and the missing-tool fallback.
   - **4j.1, diff parsing and generated-edit validation (implemented):** [Validation policy 1](FIX_VALIDATION.md) requires pinned current reviews, local generation, strict fenced output, valid Go syntax and changes confined to accepted function bodies. File/commit/revision checks precede publication. Diff parsing retains rename/copy metadata, decodes Git quoting and rejects malformed or oversized input. Final-prompt preflight follows in 4j.2.
   - **4j.2, final prompt budgets (implemented):** [Budget policy](PROMPT_BUDGETS.md) checks the full redacted provider request before dispatch, enforces input/output/context and byte limits, and distinguishes conservative estimates from billing usage. Exact-only policy refuses unsupported counts; no tokenizer dependency was added. Task packing rejects oversized first items and preserves triage batch tails. The provider panel shows the policy.
   - **4j.3, allocation reductions (implemented):** [Measurements](ALLOCATION_REDUCTIONS.md): the memory store indexes folded names at ingest and stops searching at the limit, with the old implementation kept as a fuzzed reference. `minimal_context` on 10,000 nodes drops from 94 ms and 220 MB to 1.7 ms and 2.4 MB; ingest pays about 4 ms per 10,000 nodes. Parser rules skip their regexps on lines without required literals, and the TypeScript line-owner scan became a table. Graph copies stay until callers agree an ownership rule. Numeric budgets are proposed, not enforced.
   - **4j.4, edge evidence and analysis completeness (implemented):** [Evidence fields](EDGE_EVIDENCE.md) label every resolution edge typed, syntactic or inferred (unknown on older graphs, never promoted), and versioned analysis records mark partial and truncated packages and files, build-tag exclusions, unresolved dynamic calls and bodies skipped by a per-package budget. Agents see both in symbol context, call graphs and outlines. Labelled Go and Python/TypeScript fixtures measure precision and recall. No migration; the next sync labels existing graphs. Optional SSA is deferred to 4j.4b.
   - **4j.4b, optional data-flow call analysis (implemented):** [`--dataflow` / `CODESYNAPSE_INGEST_DATAFLOW`](EDGE_EVIDENCE.md#optional-data-flow-analysis-4j4b) builds SSA for well-typed repository packages and runs VTA, adding CALLS edges with `dataflow` evidence for calls through function values. Off by default. All 16 edges it adds on this repository are correct, but it links only 6 of 4,389 dynamic sites, because most values come from outside the repository; extraction takes 39% longer. Bounded, cancellable between phases and skipped on type errors, size or failure.
   - **Neo4j removal (implemented):** HugeGraph with Milvus is the only graph database. The Neo4j store, driver, flags, compose service and manifest are gone; a configuration that still asks for Neo4j stops with an explanation, and upgraded installations re-index. Kubernetes manifests are marked outdated until 6a adds HugeGraph and Milvus.
5. **Single sign-on**: OpenID Connect login and just-in-time accounts, built on the completed tenant and session rules.
   - **5a, API (implemented):** one provider per organisation with sealed client secret, PKCE/nonce/browser-bound state, SSRF-guarded discovery and exchange, guarded email linking, passwordless just-in-time accounts, group-mapped roles and teams on provider-managed memberships, last-owner and root protection, full audit. [Plan](SSO_PLAN.md).
   - **5b, dashboard (implemented):** single sign-on on the sign-in page (with `/login?sso=<org>` links), the `/sso/callback` page, Settings → Single sign-on for owners and admins, linked identities on the profile; the proxy forwards the `cs_sso` binder on SSO paths only.
   - **5c, MCP request audit trail (planned):** today the MCP server audits only authentication failures, access denials and its few write tools. Ordinary tool calls appear only in anonymous daily usage counters. Every MCP request should be traceable afterwards to who made it, with which key, from which chat, and what it asked for.
     - **What is recorded:** every request, whether accepted, refused or failed. That covers `initialize`, list calls, `prompts/get`, `tools/call`, resource reads, transport open, resume and close, and requests refused before a tool runs (bad key, root, missing or closed runtime session, policy denial, unknown tool).
     - **Fields per event:**
       - time and request ID;
       - user ID and email;
       - organisation;
       - how they authenticated: the API key's ID, name and display prefix, never the key or its hash;
       - runtime session ID (primary and parent) and the MCP transport session ID;
       - client name and version from `initialize`, cleaned and capped, plus the bridge's version when one is used;
       - client address (trusted proxies only) and user agent;
       - JSON-RPC method, tool or prompt name and repository;
       - outcome, status and error class;
       - duration and response size.
     - **Arguments:**
       - Identifying fields are stored as values after `redact.Free` and length caps: repository, symbol or `qualified_id`, file paths, depth, limit, verbosity, memory scope.
       - Free text (queries, task descriptions) is stored redacted and capped.
       - Diffs, code, offloaded turns and other bulk inputs are never stored. They get a size and a SHA-256 digest of the canonical arguments, so a payload found later can be matched to its request.
       - Results are never stored, only their size.
     - **Storage:**
       - The same append-only, hash-chained `events` log, with new columns for runtime session, transport session, client, method, tool, repository, duration, size, argument digest and redacted arguments.
       - Appends are batched so busy agents do not serialise on the chain lock.
       - It fails closed like the rest of the audit log: if the event cannot be written, the tool does not run.
       - Same retention (`CODESYNAPSE_AUDIT_RETENTION_DAYS`), export and SIEM `audit` log line.
     - **Who sees it:** platform admins see everything. Organisation owners and admins see their organisation's MCP events in the audit view, filterable by user, key, runtime session, tool and repository.
     - **Tests:**
       - every tool in the fixed policy table produces an event, including refusals;
       - keys, key hashes and secrets in arguments never appear;
       - bulk inputs leave only a digest;
       - the chain still verifies under concurrent calls.
     - **Open decision:** how much free text to keep. Queries help tracing but can carry personal data or pasted code; the default above keeps them redacted and capped.
   - **5d, CI/CD baseline (in progress):** before 5d, the only workflows built the Homebrew formula and released the CLI on a tag.
     - **Done, pull request and merge checks:** `.github/workflows/ci.yml` runs `just ci`. The integration contracts run when stores or accounts change, and nightly. Accepted findings live in the tools' ignore files, with reasons. Actions are pinned by SHA, and Renovate updates the digests and the tools' versions.
     - **Done, images:** `.github/workflows/images.yml` builds and scans api, mcp and web on every relevant pull request, with read-only permissions. On merge and on release tags it publishes amd64 and arm64 images to ghcr.io with SBOM and provenance, signed with cosign (keyless). Tags: `:main` and `:sha-<short>` on merge; `:X.Y.Z`, `:X.Y` and `:latest` on release. Go and the web app are cross-built on the runner. The web runtime image drops npm, which was the source of its fixable vulnerabilities.
     - **Next:** the Helm checks arrive with the chart in 6a.

       - `go test -race` (`just test`), `golangci-lint` with gosec (`just lint`), and `govulncheck`;
       - the Nuxt typecheck and build (`just web-check`), plus `npm audit` for production dependencies;

       - Helm: `helm lint`, chart-testing (`ct lint`), `kubeconform` on rendered manifests;
       - `kubesec` and `kube-linter` on the rendered chart, failing on high findings;
       - Trivy config and filesystem scans;
       - the integration contracts (`just test-postgres`, `just test-hugegraph`) when stores or accounts change, and nightly otherwise.
     - **On merge to `main` (prebuild):**
       - build all three images multi-arch (amd64, arm64), scan them with Trivy, and push `:main` and `:sha-<commit>` tags to ghcr.io;
       - package the chart as a development version;
       - install it on a throwaway kind cluster and run a smoke test (health, sign-up, index a small public repository, an MCP `repo_list` through the bridge).
     - **On a release tag (`v*`):**
       - versioned, signed images (cosign keyless, provenance attestation, CycloneDX SBOM);
       - the chart published as an OCI artifact at `oci://ghcr.io/astrona-io/charts/codesynapse`;
       - the CLI binaries and Homebrew formula as today;
       - release notes generated from conventional commits.
     - **Rules:**
       - Workflows pin actions by commit SHA, run with least-privilege `permissions`, and never expose secrets to pull requests from forks.
       - Renovate keeps actions, tools and base images current, with approval for majors.
       - CI-only tools are not distributed: GPL tools such as hadolint and shellcheck are acceptable there, never inside images.
6. **Kubernetes deployment and releases (final phase)**: after the application features, access/session controls, telemetry, ingestion work and SSO are complete. Existing local development stays independent of Kubernetes, and nothing has been deployed to a production cluster. The earlier Kustomize work is parked on `feat/k8s-production`; it is reused as input for the chart, not shipped as is.

     - A Helm chart in `deploy/helm/codesynapse` replaces the Kustomize overlays.

     - The kind smoke test runs against the published artifacts before the release is marked latest.

## Standing architecture review

Every phase is checked against these constraints, taken from the architecture and security review brief. The table says where each is enforced today and which phase closes what is still open.

| Constraint | Where it holds today | Open, and where it is closed |
|---|---|---|
| **Zero-trust tenancy.** Tenant and repository come from the authenticated context, never from the model. | The tenant is never a tool argument: API routes resolve it from the session or key (`scopeOf`, `s.route` policies), MCP from the key (`Caller`, `memRepo`). `repo` is an argument, but `h.repo` and `visibleRepos` accept only graphs in the caller's scope and answer 404 otherwise. Memory traversals start at `tenant_id`/`ns`; vector searches require a tenant (`vector.ErrNoTenant`) and drop foreign hits (`vector.Isolate`). | Platform and service credentials cannot bypass content permissions. Repository-scoped readers reject foreign node IDs and traversals.
