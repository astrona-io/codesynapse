# AGENTS.md

Instructions for AI coding agents (Claude Code, Codex, Cursor, Copilot and others) working in this repository. Humans should start with `README.md`.

## What this project is

CodeSynapse indexes a repository's Go code, Markdown docs, YAML, Go templates/Helm charts, git history and dependencies (with CVEs) into a NebulaGraph property graph, then serves small, precise answers from it: symbol cards, file outlines, callers and callees, impact of a diff, a graded security review, metrics and hotspots. The point is that a coding assistant asks the graph instead of reading whole files, which cuts tokens and gives better review context.

Four services plus their stores, all in `docker-compose.yml`:

| Service | Code | Port | Purpose |
|---|---|---|---|
| `mcp` | `services/mcp` | 8090 | MCP server for AI agents (stdio or streamable HTTP) |
| `api` | `services/api` (image target `api`, no Go toolchain) | 8080 | JSON API for the dashboard; records jobs (`CODESYNAPSE_RUN_JOBS=false`) |
| `worker` | `services/api` (`codesynapse-api worker`, image target `worker`) | 8081 (health) | Runs clone, sync, index, AI and fix jobs of its roles (`--roles ingest,ai`; the `fix-worker` service runs `--roles fix`, the only one that may push) |
| `web` | `services/web` (Nuxt 4) | 3000 | Dashboard; proxies to `api` server-side |
| `nebula-graphd` (+ `nebula-metad`, `nebula-storaged`) | images | internal only | Graph store (nGQL; never published to the host) |
| `milvus` | image | internal only | Agent-memory vectors |
| `postgres` | image | internal only | Accounts, organisations, audit log |

With accounts, schedules and jobs live in PostgreSQL, and one API process at a time (the `api-loops` lease, `services/api/internal/api/singleton.go`) runs the scheduler and maintenance loops, so the API can run as several replicas.

`cmd/codesynapse` is the CLI (ingest, audit, stats, review, mcp install) for CI and local use. It is not a service.

## Use the graph before reading files

If the codesynapse MCP server is connected (`just mcp` installs it for Claude Code), use it on this repo too. Full guide with task prompts: `docs/AGENT_GUIDE.md`.

1. `minimal_context` with the task description first; read only the line ranges it returns.
2. `get_symbol_context` (verbosity "outline", then "full" before editing) for signature, risk, callers, callees, tests.
3. `get_implementations` for interfaces; never grep for interface calls. `get_call_graph` (depth 2) for deeper tracing.
4. `file_outline` before opening a file.
5. `get_pr_context` with your diff before finishing a change. Fix or justify anything it flags as untested, high risk or security-sensitive.
6. Ambiguous names return `qualified_id` suggestions: retry with one of them.
7. Before writing new code, look for what exists: `search` (and `search_all_repos`), then `duplicate_code`; reuse or extend before adding a second copy.
8. To learn what files or logs say without reading them, `ask_local` with the question and the paths; read the lines it cites before editing. For self-contained, well-specified code, `local_draft` has the local model write a draft; check it against the real file and apply it with your own edit, never blindly, and write security-sensitive code yourself.

The graph reflects the last ingest. Files you edited in this session may differ.

When you change MCP tools, prompts or the server instructions, update `docs/AGENT_GUIDE.md` in the same change. A new tool goes into one toolset in `internal/toolsets` (`TestEveryToolInOneToolset`), and instruction text that names it goes into a clause tied to that toolset (`instructionRules` in `services/mcp/internal/mcpserver/toolsets.go`).

Test the Helm chart only on the throwaway kind cluster of `just chart-e2e` (`kind-codesynapse-dev`), with `--context`/`--kube-context` set explicitly; never on a shared or production cluster. Run `just chart-check` for any chart change.

Every value lives in the chart's `values.schema.json` (and a store's in `charts/<store>/values.schema.json`): Helm checks installs against it and Artifact Hub shows it as the chart's settings. When you add, rename, remove or retype a value, change `values.yaml` and its schema in the same change, with a description and strict types (`additionalProperties: false`, enums, patterns); a value missing from the schema makes every install fail. `just chart-check` renders the chart with valid values and makes sure bad ones are refused; add a case there for a new rule.

Run `just test` and `just lint` before you call a Go change done, and `just web-check` for anything under `services/web/`. CI (`.github/workflows/ci.yml`) runs `just ci` on every pull request and merge, plus the integration contracts when stores or accounts change; run `just checks` before touching workflows, Dockerfiles, scripts or YAML. Accepted findings go in `.gitleaks.toml`/`.gitleaksignore`, `.trivyignore.yaml` or `.hadolint.yaml`, each with a reason. Pin new GitHub actions by commit SHA.

Defer both development and production Kubernetes manifest work to the final deployment phase, after application features and SSO.

## Go conventions

- Go 1.27, module `github.com/astrona-io/codesynapse`.
- Standard library first. Current dependencies: cobra (CLI), pgx (PostgreSQL), the MCP Go SDK, golang.org/x/tools and x/mod. Ask before adding any other dependency.
- Tests use the in-repo helpers `internal/testutil/assert` (continue on failure) and `internal/testutil/require` (stop on failure). Do not add testify.
- Logging is `log/slog`, carried through contexts with `internal/logx`.
- Binaries use `app.NewSubCommand` runners (`SetupFlags/Complete/Validate/Run`) from `internal/app/cli.go`; see `cmd/codesynapse/main.go`.
- `context.Context` first on anything that blocks. Wrap errors with `%w` and context. No panics outside programmer errors.
- Table-driven tests with subtests. Parsers get fuzz tests (`FuzzParseDiff`, `FuzzText`).
- Comments say why, not what. Match the density of the surrounding code.

## Adding a security rule

Rules are static files: `rules/code/<id>.yaml` and `rules/config/<id>.yaml` (see `rules/README.md` and `rules/schema.json`). They hold everything humans read (title, severity, CWE, why, fix, vulnerable → fixed examples) and are embedded with `go:embed`.

1. Write the YAML file.
2. Add detection to the detector for the language (`internal/ingest/golang/findings.go`, `internal/ingest/lang/rules.go` or `internal/ingest/config/yaml.go`), list the id in that detector's `RuleIDs`, and report findings with it.
3. Add a fixture that triggers it and one that must not to the detector's tests.
4. `just test`: `rules.TestCatalog` validates the files and `TestEveryDetectorHasARule` keeps detectors and files in sync.

## Changing the graph schema

1. Add the kind to `internal/model/model.go` and to `AllNodeKinds`/`AllEdgeKinds`. Those lists are the label allowlist for nGQL (tags and edge types are backtick-quoted from them).
2. New node fields need entries in `internal/store/nodeprops` (both directions, `TestPropsRoundTrip`) and a type in `nebulastore/schema.go` (`TestSchemaCoversNodeProps` fails otherwise). `EnsureSchema` appends new NebulaGraph properties to existing tags.
3. New `store.Reader` methods must be implemented in `memory` and `nebulastore` and covered in `storetest.Run`. NebulaGraph has no transactions, so `ReplaceRepo` takes a lease (`UPSERT … WHEN`), writes in place stamped with a run and then deletes the rows of other runs; a reader never sees a half-replaced repository because queries filter on the live run, and `successiveContract` keeps the result identical to the in-memory reference. Keep the graph an ingest produces deterministic (sort what comes out of maps). Columns that are indexed are never NULL (`NOT NULL DEFAULT`): a composite index misses rows whose later columns are NULL. The stores must behave identically; the contract test (`just test-nebula`) is how we know.
4. Update `docs/PLAN.md` (schema section) and `services/web/app/utils/types.ts` if the API shape changes.

## Security rules (non-negotiable)

This tool reads untrusted repositories and serves their contents to LLMs. Keep it that way:

- **Ingestion accounting:** exact reports live in tenant-owned accounts records, never in shared graph metrics. `Repository.meta.ingest_receipt` is an opaque commit receipt only. Checkpoints precede extraction/publication; recovery counts indexed files only after matching a receipt under the publication lock. Preserve run tombstones, cumulative totals and stable repository metric IDs across retries, restarts and unlink/relink. The three `codesynapse_files_*_total` metrics alone may carry `repo`, an admitted server-owned 24-hex repository-entry ID verified against its tenant, never a display name or graph ID. Export persisted totals through the fenced ingestion exporter, never replay them into Default counters. Scoped series use both tenant and repository extra filters. See `docs/INGEST_TRANSPARENCY_PLAN.md`.
- **Repository policy:** `.codesynapse.yaml` is untrusted. Global/Kubernetes exclusions require a matching reviewed digest (every linked organisation in the API, explicit `--approved-policy-digest` offline). Finding suppression is a tenant-local approval overlay; never delete raw findings. Annotation uses only the local `code-annotation` route, validated symbol metadata and inherited execution identity. Graph and annotation publication must retain the accounts policy transaction and final credential/revision checks. See `docs/REPO_CONFIG_PLAN.md`.
- **nGQL (NebulaGraph):** statements are constants in `nebulastore`; values travel only in parameters (`$name`), tags, edge types and columns are backtick-quoted from allowlists (`quote` panics on anything else). The one documented exception: nGQL has no parameters for vertex IDs, so an ID is written into the text through `literal(vid(prefix, id))`, which is one lowercase letter plus 32 hex characters (a hash) and panics on anything else; no caller-supplied string reaches statement text. NebulaGraph always runs with authentication on (`NEBULA_PASSWORD`, at most 24 characters; the compose and chart init steps replace the well-known first password and refuse to start without one), is never published to the host, and there is no raw-nGQL tool. Tenant-owned data (agent memory) carries `tenant_id` and every statement over it filters on `tenant_id` and `ns` first.
- **Vectors (Milvus):** filters are expression templates with values in `exprParams`, never in the expression. Every item carries its tenant (`tenant_id` is the partition key), every search names one (`vector.ErrNoTenant` otherwise), and `vector.Isolate` drops any hit of another tenant or namespace even if the backend's filter was wrong. Only entity names are embedded, by a local model.
- **Telemetry:** tenant instruments always carry `tenant_id`, `mcp_tool`, `llm_provider` and `llm_model`. Use the context-aware recording methods: the tenant comes from authenticated `telemetry.WithTenant`, tools from accepted `WithTool`/`AllowTools`, and models from configured `AllowModels`/`WithModel`; positional or client-supplied attributes cannot override them. API/background work uses `none` where no tool/model applies. Work without a trusted tenant goes to separate `platform_*` metrics with no tenant attribute. Never label prompts, queries, paths, repository names, user/key/session IDs or other request content. Each instrument caps its series before aggregation, including histogram buckets; overflow is a separate platform counter. The existing bounded registry supplies an OTel SDK `Producer` and periodic OTLP/HTTP exporter; do not record the same observation into a second SDK accumulator. `CODESYNAPSE_METRICS_EXPORTER=otlp` is the default; `prometheus` selects the legacy push format, never both for one stream. Services use the internal VictoriaMetrics URL and environment-only credentials; nothing listens for scrapes. Resource identity distinguishes service/version/environment and process instance, never a chat session. `GET /api/v1/stats/series` uses fixed MetricsQL and authenticated organisations as VictoriaMetrics `extra_filters`; ordinary panels stay scoped even for platform admins, and only explicit platform panels can query across tenants. Durable memory counts use the newest observation per tenant, deduplicate replicas and expire stale samples; never sum replica gauges. Cost without reported usage or configured prices is unknown; local execution alone proves no cloud-byte savings. New instruments go in `internal/telemetry/metrics.go`. **Traces** (`internal/telemetry/tracing.go`, docs/TELEMETRY_PLAN.md#traces): spans carry route patterns, kinds, opaque IDs, provider/model and timings, never paths, repository names, people, prompts, code, arguments, scripts or bindings. Continue an incoming `traceparent` only from trusted proxies (never in MCP). Jobs carry the queueing request's trace in `jobs.trace`. With a valid span, the request ID is the trace ID.
- **git:** only through `gitx.Run`. It disables fsmonitor, hooks, external diff and textconv, ignores global config, and never uses a shell. Validate user revisions with `gitx.ValidateRev`.
- **go list:** extraction runs with `CGO_ENABLED=0`, `GOTOOLCHAIN=local`, `GOPROXY=off` unless the user opts into network. The one other mode is the API's `--go-module-download` (`CODESYNAPSE_GO_MODULE_DOWNLOAD`, on by default, `golang.WithModuleProxy`): `GOPROXY=https://proxy.golang.org` only, checksum database on (`GOSUMDB=sum.golang.org`, no `GONOSUMDB`/`GOPRIVATE`/`GOINSECURE`), `GOVCS=*:off` so nothing is fetched from a VCS, `-mod=readonly`; only module paths and versions leave the machine. Do not loosen these defaults.
- **Filesystem:** API ingest is confined to `CODESYNAPSE_SOURCES_ROOT` after symlink resolution (`insideSources`). Docs walking never follows symlinks.
- **No source bodies or YAML values in the graph.** Store hashes, signatures, key paths, line ranges and short summaries. Every summary passes through `redact.Summary`. Author e-mails are stored only as hashes. Security findings describe the problem, never the secret.
- **Remote git:** only `gitx.Clone`/`FetchCheckout`/`RemoteBranches`. Remotes go through `gitx.ValidateRemote` (https only, no credentials in URLs, no private/loopback hosts unless `CODESYNAPSE_ALLOW_PRIVATE_GIT`). Tokens are passed as `GIT_CONFIG_*` environment, never argv, and only to their configured host. Redirects are never followed (`http.followRedirects=false`; a moved repository answers `gitx.ErrRedirected` and is added by its new URL), and the addresses `ValidateRemote` checked are pinned for git (`http.curloptResolve`, ten minutes), so a second DNS answer cannot reach an address that was not checked.
- **Organisations:** repositories are listed only through `internal/forge`, one client per host (GitHub, Forgejo/Gitea, GitLab; no redirects). Hosts other than github.com come from the user, so they pass `gitx.ValidateRemote` (https, no internal addresses unless `CODESYNAPSE_ALLOW_PRIVATE_GIT`, no ports) before any API call or clone. Tokens are per host (`CODESYNAPSE_GIT_TOKENS`, legacy `CODESYNAPSE_GIT_TOKEN` + `_HOST`), picked with `gitx.AuthFor` and sent to that host only. Clone URLs are built as `https://<host>/<login>/<name>.git` from a validated host, an allowlisted login and a `validRepoSegment` name, never taken from the API answer. Repository names carry the host except on github.com (`owner/name` vs `host/owner/name`), so identical org and repo names on two providers never collide. Scans queue at most 10 clones each and back off an hour after a failure. That watch list is single-tenant; with accounts, `POST /api/v1/imports/list` (signed-in session, Member) lists with the selected organisation's own token for that host when it has one and the caller is an owner or admin (private repositories included without descriptions, each with the token's `admin`/`write`/`read` permission; audited `git_token.list` before the call; never the token owner's own account through `/user/repos`; the token is not pinned to a namespace, hence managers only), else anonymously with public repositories only, for the dashboard, which adds picked ones through `POST /api/v1/repos` (a private one still passes `proveAccess`). Organisation watches always list anonymously and add public repositories only.
- **Dependency data:** only ecosystem, module/package names and versions leave the machine (osv.dev for vulnerabilities, deps.dev for licences not found on disk). Keep it that way.
- **Model prices** (`services/api/internal/llm/pricing.go`): cost and savings figures name where their prices come from (`price_source`, `price_checked`). The opt-in `price_feed: openrouter` downloads OpenRouter's public model list once a day with a plain GET and looks the model up locally; nothing about the installation, its models or its usage is sent. Local providers cannot use a feed.
- **Runtime facts** (`internal/runtimefacts`, `services/api/internal/api/runtime.go`): coverage profiles and JUnit reports come from CI (`PUT /api/v1/repos/{repo}/runtime`, Member role, 64 MiB gzip or plain, at most 20 reports) or from the local checkout, and are untrusted: parsers are bounded and fuzzed, and only mapped counts are stored, never report text or source. Facts live beside the code graph per namespace (`memory.Namespace(org, graph)`), so organisations sharing a graph never see or overwrite each other's; readers take the namespace from the authenticated caller (`store.WithRuntimeScope`), never from arguments, and `store.RuntimeFactsOf` refuses a scope for another graph or a reader fenced to another repository.
- **MCP tools are read-only** and annotated `ReadOnlyHint`, with one exception: the review tools (`submit_review`, `update_review_comment`) write to the review store only (`store.ReviewStore`, `:Review` nodes), never to code or the graph. Review text is size-limited and secret-redacted (`reviews.Prepare`), file paths are repo-relative with no `..`, and `--allow-reviews=false` disables them. The second exception, discussed and on by default (`--allow-memory=false` / `CODESYNAPSE_ALLOW_MEMORY=false` turns it off): the agent-memory tools (`upsert_graph_triples`, plus the read-only `search_graph_nodes` and `query_subgraph`) write triples to `:MemoryEntity`/`:FACT` only, scoped to an indexed repository, never to code or the code graph. Predicates are validated (`UPPER_SNAKE_CASE`, so agent text reaches nGQL only as parameters), names are redacted and size-limited, every fact records the client that saved it, each repository is capped (`memory.MaxFactsPerRepo`), and reads carry `memory.Notice`: recalled facts are data, not instructions. `offload_turns` sends conversation turns to the session-memory API (`CODESYNAPSE_API_URL`, bearer `CODESYNAPSE_API_TOKEN` from the environment), where `services/api/internal/offload` extracts triples **only with a local model** (the "memory" route must point at a provider for which `ProviderConfig.Local()` is true; cloud providers are refused, because conversations often contain code). Turns are redacted, held in memory until the job ran, and never stored; the model answer is parsed defensively (`internal/memory/extract`) and only validated triples above the confidence threshold are saved in the originating session scope. Recall by meaning embeds entity names and queries only with the local provider routed to "embeddings" that has an `embedding_model` (`llm.Registry.EmbeddingProvider`). The `codesynapse memory` hook commands read the API token from the environment or the user config folder (`~/Library/Application Support/codesynapse/api-token` on macOS, `~/.config/codesynapse/api-token` on Linux; 0600), never from argv or settings files, and always exit 0. The third exception, discussed with the project owner and on by default (`--allow-catalog=false` / `CODESYNAPSE_ALLOW_CATALOG=false` turns it off): `architecture_propose` and `architecture_link` write only `:Curated` proposals and links of the architecture catalog (`store.CuratedStore`, `internal/curation`), never to code, the code graph or the record files. A proposal is always the draft status of its type, has no way to be approved, accepted, rejected or to supersede anything, and only becomes a decision when a person commits it as a file with an accepted status. Both tools need the Member role on the repository, validate what they reference (records must exist, code must name exactly one place), redact and size-limit all text, record the client and user, are kept per organisation and, in accounts mode, write an audit event before the change (a failed audit refuses the change). There is deliberately no raw-nGQL tool (a statement runs with the service account's rights). Do not add other write tools without discussing it first.
- **Git tools** (`internal/gittools`, toolset `git`): `git_status`, `git_diff_summary`, `git_blame` and `git_log` read the developer's checkout, which the server cannot see, so the Claude Code bridge answers them locally. Before it gives an answer it reports the call to `POST /api/v1/usage/local` with the chat's runtime session (tool, client, the repository the checkout is, duration and answer size only; the tool must be one of `gittools.Tools`, `ghtools.Tools`, `coretools.Local`, `ask_local` or `local_draft`, and a repository the caller cannot read is dropped), where it joins the usage buckets and is written to the audit log as `mcp.local_answer`. A network error sends that one call to the server; a refused key or session (401/403) or an audit entry that could not be written (503) stops local answers for the rest of the chat, and a tool the server does not accept (400) goes to the server from then on. The server registers the tools but answers a direct call with an error. They run only through `gitx.Run`, take repo-relative paths (`gittools.CleanPath`), validated revisions and bounded limits, and return no patch text and no e-mail addresses; subjects and hunk headings pass `redact.Summary`. Keep them read-only and keep the report free of anything about the checkout beyond its repository name. `gh_pr_status` (its `wait_seconds` poll is bounded: at most 300 s, 15 s apart, and the bridge raises its per-call timeout by exactly that), `gh_pr_list`, `gh_run_failure` and `gh_run_list` (`internal/ghtools`, same toolset; `gh_run_list` filters by workflow, branch and conclusion after `gh` answers, so no agent text reaches its arguments; the failure log is parsed in the bridge, never sent to a model) follow the same rules: answered by the bridge with the developer's own `gh` sign-in (the server never holds a GitHub token), started without a shell with a fixed argument list where only validated numbers and enums vary, output capped, no URLs, bodies or e-mail addresses in the answer, titles and check names through `redact.Summary`. Do not add a gh tool that creates, merges, closes or comments.
- **ask_local** (`internal/asklocal`, toolset `core`): the bridge reads files of the developer's checkout and sends them, with the agent's question, to `POST /api/v1/repos/{repo}/ask-local` (Member, runtime session), which answers only through the local-only `local-answer` task (`llm.LocalTasks`), so source never reaches a cloud model this way and there is no cloud fallback (409 tells the agent to read the files itself). The bridge reads only files git tracks (`git ls-files`, so ignored files such as `.env` are refused), through `gittools.CleanPath`, never follows symlinks and skips binaries and files over `asklocal.MaxFileBytes`; requests are bounded by `asklocal.MaxFiles`, `MaxTotalBytes` and `maxAskBatches`. The files are used for one request and never stored or logged. The answer is model output: thinking is stripped, it passes `redact.Free`, is capped at `asklocal.MaxAnswer`, and its citations are checked against the lines sent. The call is reported to `POST /api/v1/usage/local` like the git tools. The plugin's pre-brief hook (`codesynapse hook brief`) uses the same endpoint with `mode: "brief"` for the files `POST /api/v1/repos/{repo}/brief-plan` names (graph only, Viewer); the briefing is added as context beside the prompt, never replaces or blocks it. `local_draft` (same toolset and package, `draft.go`) has the same bridge rules and posts a task and the files to `POST /api/v1/repos/{repo}/local-draft` (Member, runtime session), which runs only on the local-only `local-draft` task with a constant system prompt and no cloud fallback (409), in one request (413 when the files do not fit; no batching). The draft is model output, checked before the agent sees it: thinking stripped, `redact.Free`, capped at `asklocal.MaxDraft`, a diff parsed with its paths limited to the files sent or the target and its lines matched against the lines sent, Go parsed with `go/parser`; every draft carries `asklocal.DraftWarning`. It never writes files: the agent applies the draft with its own edit. Drafts are counted as `usage.LocalDrafts`, with no tokens-avoided figure.
- **MCP usage counters** (`internal/usage`, on unless `--record-usage=false` / `CODESYNAPSE_MCP_USAGE=false`): the MCP server adds daily aggregates per repository, tool and client (calls, errors, response size, latency) to `:McpUsage` nodes for the Statistics page. Only the `repo` argument is read; other arguments and results are measured, never stored in the counters (the audit log keeps redacted arguments, see below). Client names are cleaned and capped, buckets between flushes are bounded, and data older than 180 days is pruned. The Claude Code plugin adds `ranges_returned`/`ranges_read` to the same buckets through `POST /api/v1/repos/{repo}/usage/retrieval` (Viewer, known tool names and bounded counts only): its hooks keep the answered `file:start-end` ranges in the local session state file and send per-tool counts, never paths, ranges or session IDs. The same report carries workflow counts (`first_codesynapse`, `first_native`, `reads_turned_back`: how a session began and how many whole-file reads the guard turned back; `files_edited`, `files_edited_found`: how many indexed files the session changed and how many of them an answer had named, computed from the session's start point kept in the local state file; with `CODESYNAPSE_EVAL_CAPTURE=true` the session's first prompt, redacted with `redact.Free`, and its changed files are kept as an eval case in the checkout's git directory and never sent), the Bash hook (`cmd/codesynapse/bash.go`) adds per-class counts of shell commands a CodeSynapse tool answers with less output (`usage.BashClasses`, report field `bash`; classes only, never commands), and these are stored as pseudo-tool buckets (`usage.IsWorkflow`) that never count as tool calls. The Stop hook reports a checkout the server has not indexed to `POST /api/v1/usage/unindexed` (any signed-in caller; the origin-derived repository name and client only, at most 200 distinct names per organisation per day), stored as the `usage.Unindexed` pseudo tool with the organisation but no repository, so Statistics can recommend indexing it; the avoided-tokens figure beside it is a reference from indexed repositories, never a measurement of the skipped checkout. The ruleset sessions start with is `internal/agentrules`, served at `GET /api/v1/agent-rules` (any signed-in caller; `CODESYNAPSE_AGENT_RULES_FILE` replaces it, at most 4 KiB); keep it free of secrets and project data. The bridge sends the client's own name (`X-CodeSynapse-Client`, from `initialize`) with every request, and the MCP service falls back to it when the SDK has no client info, so calls no longer count as `unknown`; usage cleans and caps it like any client name. Bucket updates run under the graph lock because the MCP recorder and the API both add to them.
- **Destructive API actions** (delete repository, delete review) are confirmed in the UI; the one automatic removal is `reapIfGone` (scheduler): a cloned repository goes only after the provider API answers a clean 404 three scheduled syncs in a row; deleting cloned files is limited to a single directory inside the workspace, and mounted sources are never deleted.
- **Network services** refuse to bind a non-loopback address without a bearer token (`app.ErrTokenRequired`). The web proxy (`services/web/server/api/cg`) rejects cross-origin mutating requests and, with accounts, forwards only the browser's `cs_session` cookie (and the `cs_org` slug as `X-CodeSynapse-Org`), never the API token: a visitor is exactly who they signed in as. Only single-tenant installs get the server-side token, and an unreadable mode fails closed. The API takes the client address from `X-Forwarded-For` only from `CODESYNAPSE_TRUSTED_PROXIES` (login limits and audit IPs are per user, not per proxy). `/api/v1/settings` shows the installation's Git token previews to platform admins only.
- **Limits everywhere:** `store.MaxLimit`, `store.MaxDepth`, request body caps, query timeouts. New endpoints keep them.
- **Pushing:** only `services/api/internal/fixes` pushes, only when `CODESYNAPSE_ALLOW_PUSH=true`, only in a worker with the fix role (`fix-worker`, `fixWorker.enabled`; `pushAllowed` ignores the switch in any other worker, and no worker holds `CODESYNAPSE_API_TOKEN` or the administrator password; installation push tokens, `CODESYNAPSE_GIT_PUSH_TOKENS`, go to the fix worker only), only through `gitx.PushBranch` (new `codesynapse/*` branches, never forced) from a separate worktree, and never edits CI or git configuration (`fixes.protected`). Keep those rails.
- **LLM calls:** only through `services/api/internal/llm`. Model output is untrusted: parse it defensively, validate enums and file paths, redact before storing. Prompts and embedding inputs pass `redact.Free` (secrets and personal data) in the registry, so no caller can skip it. Free text people or agents write (memory, offloaded turns, reviews) also goes through `redact.Free` before it is stored; new free-text stores do the same. Keep system prompts constant: the Anthropic provider caches them as the prompt prefix, and anything per-request belongs in the user part. Never send source to a non-local provider except a diff the user asked to review. API keys come from `api_key_env`, never from `config/llm.yaml` itself.
- **Accounts** (`internal/accounts`, PostgreSQL via `CODESYNAPSE_DATABASE_URL`, env only): passwords are argon2id; session tokens and API keys (`csk_…`) are stored only as SHA-256 hashes; sessions are HTTP-only `SameSite=Lax` cookies; logins are rate limited through PostgreSQL (`TakeAttempt`, hashed keys), so every API replica shares the count, and unknown emails take as long as wrong passwords; API keys act in one organisation and stop working when the member is removed; cookie-authenticated changes must be same-origin. Never return a password hash or key hash from an endpoint.
- **Tenant scoping:** every API route is registered with `s.route(pattern, policy, handler)` (`services/api/internal/api/scope.go`): `repoRole`/`reviewRole` (a role on the repository's organisation; others' repositories answer 404), `visibleOnly` (the handler filters with `visibleRepos`/`scopeFrom(ctx).sees`), `orgRole` (a role in the selected organisation, `X-CodeSynapse-Org` or the API key's), `anyone`, or `platformOnly`. Pick the narrowest; a new list endpoint must filter. Organisations add public repositories only (cloned without the installation's tokens); an already indexed graph is linked, not cloned again; deleting removes the organisation's link and the graph only with the last link.
- **Organisation Git tokens and private repositories** (`services/api/internal/api/orgtokens.go`, `internal/accounts/gittokens.go`): tokens are sealed with AES-256-GCM (`accounts.Sealer`, key from `CODESYNAPSE_SECRET_KEY`, env only; the ciphertext is bound to organisation and host), set and removed by owners and admins only (never with an API key), shown as previews, opened only to clone, fetch, push or list the organisation's repositories for a signed-in member (`imports/list`), and never logged, returned or audited in clear. Organisations never use the installation's tokens: a public repository is cloned anonymously, a private one only after the organisation's own token read it (`proveAccess`, one `ls-remote`). An existing graph is linked only for the same remote (`sameRemote`), so a name cannot open someone else's graph. Every sync re-checks each organisation's private access (`verifyAccess`): `gitx.ErrNoAccess` or a missing token marks the entry `lost` (hidden from API and MCP scope, audited `repo.access_lost`), network errors change nothing, and a working token restores it. Fix branches of organisation members push with the organisation's token (`pushAuth`).
- **Organisation watches** (`services/api/internal/api/watches.go`, `internal/accounts/watches.go`, migration 0024): a member can ask for the public repositories an organisation or user on a git host creates later to be added to their CodeSynapse organisation. Created, paused and removed only from a signed-in session (never an API key), Member role, audited before the change; at most `accounts.MaxWatchesPerOrg` per organisation. What exists at creation is the baseline (`Known`), so only later repositories are added, at most `maxClonesPerScan` per scan. The scan runs in the scheduler loop (so under the `api-loops` lease) as the creating member: it rebuilds their execution session, membership and Member role every time and records `needs sign-in` or `paused` instead of acting when any is gone; a creator opening Repositories renews the delegated session (audited). It lists anonymously and adds only public repositories through the same checks as `POST /repos` (`ValidateRemote`, `publicRemote`, `sameRemote`, a durable clone job); each add writes a `watch.repo_add` audit event first. This is the one place besides a signed-in session that may attach a repository: `signedInOrWatching` accepts the `automation` principal only when `watchContext` set the private marker. Private repositories are never auto-added.
- **Repository permissions** (`internal/accounts/authz.go`, `teams.go`): PostgreSQL memberships and relation tuples are authoritative. Every subject must be an active, explicit member of the owning organisation; platform administration gives no code access. A direct user grant (`admin`, `editor`, `viewer`, or explicit `none`) overrides team grants; otherwise the strongest same-organisation team grant wins, then the organisation's `READ_ONLY`/`NONE` default. Guests receive no default. Organisation roles manage membership and policy without granting repository permissions. API keys stay in their selected organisation and never mutate access. `AccessOf` uses bounded bulk reads; overflow or invalid grants fail closed. `Access.Scope` excludes unselected and ambiguous tenant entries. Memory/review writes need editor; sync, schedules, settings and grants need repository admin. Creating or attaching an organisation repository requires a signed-in session and records an initial explicit admin grant atomically. Voluntary access changes preserve an active repository admin; security revocation and suspension still apply immediately. An explicit organisation owner can recover administration through an audited action. External grants remain inactive without membership.
- **Access projections** (`internal/model/access.go`, `internal/query/access.go`, store adapters): `Organization`, `User`, `Team` and `AccessRepository` are separate from code `Node` vertices. Access relationships never attach to packages/functions. Versioned snapshots contain tenant IDs, opaque subject IDs and permissions, never credentials or user emails. PostgreSQL policy mutations commit audit and outbox records together. A bounded worker rebuilds projections; missing, conflicting or stale projections cannot authorize requests. Keep nGQL statements constant, with values only in parameters. The shared store contract tests permission parity and revision handling.
- **Execution identity:** every MCP tool and API execution action requires accounts and a registered runtime session (`internal/execution`, `internal/accounts/execution.go`). HTTP carries `X-CodeSynapse-Session` and `X-CodeSynapse-Parent-Session`; stdio uses the corresponding `CODESYNAPSE_SESSION_ID` and `CODESYNAPSE_PARENT_SESSION_ID` startup values. Primary and parent are equal, immutable, supplied by the runtime and bound to one tenant/user. Never generate a fallback or select scope from tool arguments. The one server-side binding is the dashboard's: a request authenticated by a browser session cookie that names no runtime session gets `accounts.DashboardExecutionSession`, derived from the login session's hash, the selected organisation and a seven-day window and registered like any other; API keys and the service token never get one, and explicit headers are never replaced by it. Jobs, model calls and subprocesses inherit the validated identity and recheck permissions before work/persistence. Accountsless automation fails closed. Claude Code connects through `codesynapse mcp bridge` (stdio, one per chat), which takes the ID Claude Code supplies in `CLAUDE_CODE_SESSION_ID`, registers it and adds the headers; it never generates one. While the checkout has unsynced changes, the bridge answers `coretools.Local` for that repository from a working-tree graph it builds locally (`cmd/codesynapse/worktree.go`); this is the default for the Claude Code bridge (`CODESYNAPSE_BRIDGE_WORKTREE=false` or `--worktree=false` sends every call to the server; the `--client` runtime adapters never use it). Those answers read only local files and send no code to the server, but every one is reported to `POST /api/v1/usage/local` like the git tools, before the answer is given and with the chat's session, so it is counted and audited (`mcp.local_answer`); when the server refuses or cannot record it, the call goes to the server. The project owner wants every request audited and counted. A build that failed is not repeated until the tree changes, and a `.codesynapse.yaml` that needs approval is not built locally until the file changes. Keep them to tools that read one repository's code graph; anything that needs stored data, another repository or a write goes to the server. Register with `POST /api/v1/execution/sessions`; seven-day expiry and revocation retain permanent tombstones. Session IDs never become metric labels. See `docs/SESSION_CONTEXT_PLAN.md` for client compatibility and limits. Jobs are durable with accounts (`internal/accounts/jobs.go`, `services/api/internal/api/jobs_durable.go`): every new job needs `JobOptions.Durable` (stored parameters, never credentials), and a resumed job is rebuilt only through the function that built it, after `jobContext` rechecked session, account, key, membership and permission. Fix jobs are never resumed. A job stopped by its process stopping or by lost leases (`errLeaseLost`, renewal failing for 90 s) is never marked failed: its record stays for another process (`leftBehind`).
- **Session memory:** `offload_turns` writes only session-private `SessionMemoryEntity`/`SESSION_FACT` data; `recall_context` defaults to the tenant/session/namespace, with explicit `memory_scope: "repository"` for durable recall. Session vector collections are separate and filter tenant/session/namespace/expiry with `exprParams`; foreign hits are discarded before graph hydration. Existing triple tools remain durable repository memory. New durable facts record `origin_session_id`; legacy facts are not assigned invented sessions. Promotion is an explicit authorised API action. Clearing or expiring session memory retains replay tombstones and removes its vectors. No anonymous background embedding: refresh requires the originating session. Raw turns are redacted, bounded, transient and extracted only by a local model.
- **MCP tenant scoping:** with `CODESYNAPSE_DATABASE_URL` set, HTTP and stdio require personal API keys. The installation token and an absent `Caller` grant no content access. Authentication and permissions are checked on every tool invocation, including resumed sessions. Every tool appears in the fixed policy table; unknown tools fail closed. `h.repo` and `visibleRepos` limit graph selection; `store.ForRepository` fences node IDs, graph traversals and contextual answers. Memory uses the `org|graph` namespace; reviews require the exact organisation (legacy organisation-less reviews are unavailable in accounts mode). Calls to the API forward the caller's own key. Background work carries actor and organisation identity and rechecks credentials and permission before execution and writes. Schedules require explicit delegated identity and current repository admin. Explicit offline/single-tenant mode remains available without accounts.
- **Audit log (NIS2):** every changing request and every security event is recorded with actor, how they authenticated, client address, user agent, request ID, target, status and outcome, in an append-only, hash-chained table (`events`, tip in `audit_head`, appended under a row lock) with `GET /api/v1/admin/audit/verify`, export as JSON, JSON Lines or CSV (formula-neutralised), and a structured `audit` log line for SIEMs. New endpoints are covered automatically by the HTTP middleware; new security-relevant actions in services also call `Service.Record` with a semantic action. Retention is `CODESYNAPSE_AUDIT_RETENTION_DAYS` (default 400, minimum 30). With an archive (`internal/auditarchive`: `CODESYNAPSE_AUDIT_ARCHIVE_DIR` or an S3 bucket, SigV4 from the standard library, https only, no redirects, keys from the environment and only in the API), entries older than `CODESYNAPSE_AUDIT_HOT_DAYS` are sealed into gzip files in ID order and leave PostgreSQL only after the file is stored and its row (`audit_segments`: range, boundary hashes, SHA-256) is written under the `audit_head` lock; only the oldest file is ever dropped, so the chain keeps one anchor. Sealing runs under the `api-loops` lease; with sealed files and no archive, pruning stops instead of breaking the chain. **MCP requests** are audited too (`services/mcp/internal/mcpserver/audit.go`, docs/SAAS.md 5c). Every request except `ping` and notifications becomes an `mcp.<method>` entry, accepted or refused. It records the caller, the API key ID (never the key or its hash), the runtime and transport session, the client, the tool or prompt, the repository, duration, response size, a SHA-256 digest of the canonical arguments, and the arguments themselves: values pass `redact.Free` and are capped at `accounts.MaxMCPArgValue`, while bulk inputs (`diff`, `code`, `turns`, …) and longer values keep only a digest and size. Results are never stored. If the entry cannot be written, the result is withheld. MCP details are an optional `Event.MCP` block that joins the hash chain only when present, so older entries still verify. The client address comes from `RequestInfoHTTP`, which sets `X-CodeSynapse-Client-Addr`/`-Request-Id` itself; client-sent copies are overwritten. The MCP service trusts no proxy unless `CODESYNAPSE_MCP_TRUSTED_PROXIES` is set in compose.
- **Bootstrap root** (`internal/accounts/bootstrap.go`, `initialadmin.go`, `services/api/internal/api/root.go`, migrations 0010 and 0020): an empty installation creates its root at API start-up as `admin` with a random per-installation password (`CODESYNAPSE_ADMIN_PASSWORD` from `.env` or the chart's `<release>-admin` Secret; unset, one is logged once, the only place a password may be logged; `change-me*` placeholders are ignored; `CODESYNAPSE_AUTO_ADMIN=false` turns it off). Never add a fixed or shared default credential. That auto-created root alone can be replaced by the operator's own (`ReplaceRoot`, audited) and `codesynapse-api reset-admin` resets it (audited, operator only). Otherwise the first account is the installation's immutable root (one per installation, never cleared; independent of the platform-admin flag). Root does governance only; `businessAllowed` refuses it in `accessOf`, `RoleIn`, API-key authentication, org creation and execution sessions, so memberships, grants, keys, jobs and schedules cannot bypass it. Every API route is registered through `s.route` (policy, `governance(...)` for root-allowed routes) or `s.account` (public/governance/business); `TestEveryRouteIsClassified` keeps it that way, and new routes default to business. Its only tenant change is `CompleteSetup` (organisation + distinct standard owner + completion + session end in one transaction). Existing installations are classified once at API start-up from setup history; an ambiguous one limits every platform admin until `codesynapse-api designate-root`. Single-tenant mode has no accounts and no root.
- **Single sign-on** (`internal/sso`, `internal/accounts/sso.go`, `services/api/internal/api/sso.go`, migration 0011; see `docs/SSO_PLAN.md`):
  - **Providers:** one OpenID Connect provider per organisation, set by owners and admins in a signed-in session. The issuer passes discovery before it is stored. The client secret is sealed with `accounts.Sealer` bound to purpose, organisation and issuer, and only its preview is shown.
  - **Network:** all provider traffic goes through `sso.Client`, which refuses internal addresses at dial time unless `CODESYNAPSE_SSO_ALLOW_PRIVATE`, follows no redirects, caps responses at 1 MiB and needs https endpoints.
  - **Sign-in:** PKCE S256, a nonce, a single-use state stored as a hash and bound to the browser's `cs_sso` cookie, and verified ID tokens only. No step redirects through the API.
  - **Accounts:** a new subject needs a verified email. It links an existing account only if that account is already a member of the provider's organisation, and gets a passwordless account only when the provider grants a role.
  - **Membership:** the provider's groups manage only the memberships it created (`idp_memberships`) and mapped teams. Hand-added memberships are untouched. The last owner is never removed or demoted. Root and suspended accounts never sign in this way.
  - **Audit:** every step is audited.
- **Platform administration** (`/api/v1/admin/*`, platform admins only; suspending and the platform admin flag need a signed-in session, never an API key): suspending an account (`users.disabled_at`) ends its sessions and refuses its logins and keys at the next request; the service keeps at least one active platform admin (`ErrLastAdmin`) and refuses suspending yourself. Admin user lists never carry password hashes.
- Secrets come from the environment (`CODESYNAPSE_NEBULA_PASSWORD`, `*_TOKEN`), never flags, never logs.

## Web (Nuxt 4)

Human identity reviews: `code_identity_reviews` only reads. Only the web API's
signed-in repository-admin route can create same-symbol, copy or distinct
reviews in accounts mode; API keys cannot. They are organisation-scoped,
revision-pinned `Curated` evidence, audited before saving. Same-symbol reviews
provide aliases for retired IDs without changing shared graph identities.
Concurrent conflicting heads fail closed; superseded evidence is retained.
Policy exclusions apply to saved review paths as well as current symbols.
Never add an MCP identity-review write or automatically collapse live copies.

Code identity and reuse: `code_identities` reads permanent symbol IDs and
revision-specific evidence; `code_records` reads attributed annotations and
explicit lineage. `code_annotate` and `code_record_reuse` are approved narrow
catalog writes under the existing `--allow-catalog` switch: `Curated` records
only, organisation-scoped, write permission required and audited before writes
in accounts mode. They never edit code, approve decisions, resolve identities
or propagate changes. Free text is redacted and bounded. Reuse pins original
and destination IDs/revisions/fingerprints and the author's licence,
attribution, compatibility and validation assessment. Reads flag changed or
unavailable evidence without rewriting history. Uncertain matches are data for
review, never verified lineage. Provenance may name one source repository in
the same selected organisation: creation requires source read access and
destination write access. Every read rechecks source access and hides the
whole record if it is lost, including free text and source identifiers.
An authorised but unavailable source is flagged, never treated as clean.
See `docs/AGENT_GUIDE.md` for contracts and limits.

- `services/web/app/` is the source dir. Pages under `app/pages/repos/[repo]/`.
- All data goes through `useApiGet` / `apiPost` in `app/composables/useApi.ts`, which hit `/api/cg/*`. Never call the Go API from the browser directly.
